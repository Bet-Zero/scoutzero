# ARCHITECT WORLD TIME ISSUE LOG

## STEP 1 — League / World Time / As-Of Ownership and Source of Truth

| Issue ID | Related Step(s) | Severity | Description | Status |
|----------|-----------------|----------|-------------|--------|
| WT-1-1 | WT-1A | MEDIUM | Active world lifecycle ownership is split: `WorldSelector.tsx` owns localStorage restore/persist of `worldId` and invalid-world cleanup internally, rather than this being fully driven through `useArchitectState.ts`. The state hook is the real owner of `worldId`, but the full active-world lifecycle (restore, persist, invalidate) does not yet flow entirely through the central state layer. | RESOLVED — restore, persist, and invalid-world cleanup now live in `useArchitectState.ts` and flow through `activeWorldOwner`. |
| WT-1-2 | WT-1B | MEDIUM | World date / as-of mutation ownership is widget-owned: `WorldTimeControls.tsx` calls `updateWorldMetadata(...)` directly and pushes the result back into state via `setAsOfDate(...)`. The state hook owns the stored date value, but the mutation path bypasses it entirely. Mutation ownership does not match state ownership, creating a split seam that mirrors the world selection problem. | RESOLVED — world-date metadata mutation now lives in `useArchitectState.ts` and flows through `worldTimeOwner`. |
| WT-1-3 | WT-1C, WT-1D | LOW | The world-vs-no-world policy boundary is coherent but distributed across at least four separate layers (`WorldSelector.tsx`, `WorldTimeControls.tsx`, `useArchitectState.ts`, `GMDashboard.tsx`), with no single named policy seam and no focused guardrails protecting it. The ownership seams for world/time state are currently readable but depend on informal convention rather than structural enforcement, making slow drift plausible as downstream features accrete. | RESOLVED — the hook now publishes a named `worldModeBoundary` contract and focused tests/guardrails pin sandbox vs world-backed behavior across the hook, dashboard, and selector seam. |

## STEP 2 — World Selection Lifecycle and Persistence Truth

| Issue ID | Related Step(s) | Severity | Description | Status |
|----------|------------------|----------|-------------|--------|
| WT-2-1 | WT-2A | MEDIUM | Archive and delete lifecycle actions do not each route through one explicit persistence owner. The UI archives by calling `updateWorldMetadata(..., { isArchived: true })` directly instead of routing through the dedicated `archiveWorld(...)` helper that includes a permission check. The persistence module still exposes a deprecated `deleteWorld(...)` path alongside the real full-delete path `purgeWorld(...)`, creating a duplicate lifecycle surface even though the UI currently uses the correct path. | RESOLVED — archive now routes through `archiveWorld(...)`, and the misleading metadata-only `deleteWorld(...)` helper was removed so `purgeWorld(...)` remains the sole permanent-delete owner. |
| WT-2-2 | WT-2B | MEDIUM | The active-world selection lifecycle (restore, persist, invalidate, switch, clear after archive/delete) is centered in `useArchitectState.ts` after Step 1 but still lacks explicit durability as one coherent lifecycle model. The seam connecting widget flow, state ownership, and persistence outcomes across all transition cases has not been fully hardened, leaving restore/switch/clear edge cases without structural enforcement. | RESOLVED — `useArchitectState.ts` now centralizes restore/persist/invalidate/switch/clear through shared lifecycle helpers and clears world-derived transient state whenever the active-world selection changes. |
| WT-2-3 | WT-2A, WT-2B, WT-2C | LOW | World selection lifecycle truth depends on informal convention rather than focused structural guardrails. Core lifecycle assumptions — the selector remaining a control surface, archive/delete routing through intended persistence paths, restore/persist/invalidate/switch flowing through the state owner, deprecated helpers not quietly becoming active again — have no focused protection. Drift in any of these seams can silently distort downstream Architect behavior without immediately appearing broken. | RESOLVED — WT-2C added focused state-owner behavior guardrails, selector control-surface behavior/source guardrails, and persistence-surface export/source guardrails that pin the intended Step 2 lifecycle seams. |

## STEP 3 — World Date / As-Of Control and Persistence Truth

| Issue ID | Related Step(s) | Severity | Description | Status |
|----------|-----------------|----------|-------------|--------|
| WT-3-1 | WT-3A | MEDIUM | The visible as-of date and the `+1 Day` increment both have an implicit synthetic fallback that is not authoritative persisted world truth. `WorldTimeControls.tsx` computes `displayDate = asOfDate \|\| new Date().toISOString().slice(0, 10)` and signals the gap only with a `(System)` badge — the displayed value is not yet persisted world metadata. `advanceByOneDay()` in `useArchitectState.ts` seeds from `worldAsOfDate \|\| getIsoDateString()` using the same system/UTC source, so the first increment is also not anchored to stored world state. Both fallbacks are incidental rather than explicitly designed, leaving the as-of truth policy implicit and the first-mutation story incomplete. | RESOLVED — the control now renders only saved world `asOfDate` truth (blank/unset otherwise), `+1 Day` is disabled and hook-rejected until a saved date exists, and the increment path now uses UTC-safe ISO date math instead of a synthetic local/system fallback. |
| WT-3-2 | WT-3B | MEDIUM | User-facing date mutation failures are silently swallowed rather than surfaced to the user. `WorldTimeControls.tsx` catches errors from both direct date input and `+1 Day` but only calls `console.error(...)` — no focused control-level error state is shown. A failed write therefore behaves as a soft no-op from the user's perspective: no feedback is given, the displayed date may appear unchanged or correct, and the user has no way to know the persistence write did not land. | RESOLVED — the control now shows inline save/advance failure messages, preserves owner-driven in-progress state, and restores failed direct edits back to the last saved world date so mutation failures are visible rather than console-only soft no-ops. |
| WT-3-3 | WT-3C | LOW | The persistence helper is looser than the owner contract it serves. `worldManager.updateWorldMetadata(...)` accepts `asOfDate?: unknown` with no format or shape validation, while the live owner path in `useArchitectState.updateAsOfDate(...)` enforces a non-empty string before calling it. The persistence surface itself remains a generic metadata write layer — any caller can pass a malformed or missing date value without rejection at the boundary. The main path is correct today, but the persistence contract is weaker than the control/state seam above it would suggest. | RESOLVED — `worldManager.ts` now exposes a dedicated `updateWorldAsOfDate(...)` helper that validates `YYYY-MM-DD` input and writes the authoritative date, while `updateWorldMetadata(...)` explicitly rejects `asOfDate` so callers cannot quietly keep using the looser generic path. |

## STEP 4 — World-Aware Loading, Reload, and Downstream State Application

| Issue ID | Related Step(s) | Severity | Description | Status |
|----------|-----------------|----------|-------------|--------|
| WT-4-1 | WT-4A | MEDIUM | Post-mutation world reload and reapply ownership is split between two hook seams. `useArchitectState.ts` owns the full authoritative reload path via `reloadActiveWorldTeamData()`, but `useArchitectActions.ts` also contains lighter mutation-side sync/reload paths — `syncTeamFromMutationResult(...)`, direct `loadWorldTeamData(...)` reloads, and inline roster-index refreshes — that run in parallel rather than routing through the central owner. World-backed downstream state after a mutation therefore depends on which reload path ran, not on one canonical reapply contract. | RESOLVED — the shared `reloadActiveWorldTeamData(...)` seam in `useArchitectState.ts` now accepts committed world snapshots/metadata hints and owns the post-mutation reapply path. `useArchitectActions.ts` resolves committed team truth, then delegates metadata refresh, roster-index refresh, and downstream state reapplication back through that hook-owned seam. |
| WT-4-2 | WT-4B | LOW | Downstream world metadata truth is not fully centralized through the main state owner. `useArchitectState.ts` owns `worldAsOfDate` loading from `getWorldMetadata(worldId)`, but `OffseasonSection.tsx` independently issues its own `getWorldMetadata(worldId)` call to maintain a local `worldSeason` state for season-advance UI. That creates a parallel section-local metadata read path outside the hook-owned contract, meaning world metadata can become partially stale after reload or mutation without the section state reflecting the updated truth. | RESOLVED — world metadata loading now lives in `useArchitectState.ts` for both `worldAsOfDate` and `worldCurrentSeason`, `GMDashboard.tsx` passes that central truth downstream, and `OffseasonSection.tsx` consumes the fan-out props instead of maintaining its own `getWorldMetadata(worldId)` / `worldSeason` ownership path. |
| WT-4-3 | WT-4C | LOW | The world-aware downstream state depends on multiple coordinated read/apply seams that remain implicit rather than unified. Team snapshot loading (`loadWorldTeamData(...)`), world metadata loading, league-backed roster-index refresh (`getLeague(...)`), and player override merge (`worldPlayerOverrides` → `worldAwarePlayers`) are each structurally correct in isolation, but the coordination between them is maintained by informal convention rather than one explicit reload contract. Base-mode and world-mode team loading also differ structurally. The feature works today, but there is no defined boundary that guarantees all four seams reapply together — partial refreshes that leave one part of the bundle stale are possible without any component clearly breaking. | OPEN |
