# ARCHITECT CAP SHEET — ISSUE LOG

Underlying system problems identified during Cap Sheet review.

---

## Step 1 Issues — Cap Totals Source of Truth

| Issue ID | Related Step(s) | Severity | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Status   |
| -------- | --------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| CS-1-1   | CS-1A           | HIGH     | Row-level display and canonical totals apply different rules for two-way cap treatment. `CapSheet.tsx` explicitly zeroes two-way cap hit at the row level, but `computeTeamCapTotals(...)` does not exclude two-way players from `playersTotal`. If any two-way player carries a non-zero cap hit in their contract-year slice, the Cap Sheet will display one number at the row level and a different number in the totals layer — silently.                                                                                                                                   | RESOLVED |
| CS-1-2   | CS-1C           | MEDIUM   | The canonical totals engine carries multiple legacy dead-money compatibility branches (`deadCap`, `waivedContracts`, `stretchHistory`, flat `deadMoney`) that exist alongside the live canonical input path. These branches make it harder to determine which dead-money shape the engine actually expects, increase the surface area for drift, and obscure the canonical contract boundary inside the engine itself. CS-1C narrowed this by separating canonical `deadCap` ownership from compatibility-only fallback helpers and pinning fallback behavior in focused tests. | RESOLVED |
| CS-1-3   | CS-1B, CS-1D    | MEDIUM   | The ownership boundary of `computeTeamCapTotals(...)` was implicit rather than declared. It was not clearly documented what the function owned versus what adjacent surfaces (exception eligibility, TPE display, validation cap-math) were expected to own independently. CS-1D resolves this by explicitly classifying canonical totals ownership, player-only validation/projection math, and adjacent consumers directly in code and guardrail tests, so nearby cap math no longer reads like an alternate totals authority.                                                | RESOLVED |

## Step 3 Issues — Full Cap Table / Multi-Year Truth

| Issue ID | Related Step(s) | Severity | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Status   |
| -------- | --------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| CS-3-1   | CS-3A, CS-3D    | HIGH     | Multi-year player-year row cells previously rendered `getContractYearSlice(...).salary ?? capHit` while canonical future-year totals flowed through `getPlayerCapHitForYear(...)`, leaving veteran-min treatment, two-way exclusions, and future cap-hit-vs-salary distinctions free to drift between visible rows and the yearly `Total Cap` row. CS-3A resolves the row-value seam by centralizing multi-year row display and canonical player counting through shared `getPlayerCapSheetAmountsForYear(...)`, updating `CapSheetFull.tsx` to render canonical cap hit with a guarded base-salary hint when needed, and adding focused UI/source-scan/behavioral guardrails for future-year row-to-total parity. CS-3D closes the remaining durability gap with a mixed future-year parity guardrail that sums shared row-value semantics against canonical `playersTotal` while keeping non-player allocations outside player-body math. | RESOLVED |
| CS-3-2   | CS-3B           | HIGH     | The multi-year table used to build its visible player population from players who had a contract slice in the current year, so a player with no current-year row but a future-year contract could still affect future-year totals through `computeTeamCapTotals(...)` while being silently omitted from the visible table body. CS-3B resolves this by deriving the visible player body from the displayed seven-year contract window, keeping current-year players first while appending future-only contributors in sensible future-year order, and adding focused guardrails that pin future-only row visibility plus yearly-total coherence.                                                                                                                                                                                                                                                                                            | RESOLVED |
| CS-3-3   | CS-3C, CS-3D    | MEDIUM   | The Full Cap Table presented three parallel surfaces — custom player rows, a separate cap-holds detail table, and a canonical yearly total row — without making the hierarchy between them structurally explicit. CS-3C resolves the display-coherence portion by labeling the multi-year player-detail, canonical yearly totals, and cap-holds detail surfaces directly in `CapSheetFull.tsx`, adding compact copy that clarifies `Total Cap` as the canonical yearly totals destination while player rows and cap holds remain supporting detail, and pinning those hierarchy signals in focused UI/source-scan guardrails. CS-3D completes the body-level durability piece by asserting that visible future-year player-body sums stay aligned with the canonical totals row while future-year cap holds remain separate supporting detail rather than a shadow totals surface.                                                          | RESOLVED |

## Step 5 Issues — Cap Sheet Mutation Paths, Save/Persist, and Final Validation

| Issue ID | Related Step(s) | Severity | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Status |
| -------- | --------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| CS-5-1   | CS-5A, CS-5D    | HIGH     | Dead money and exception edits converge on one audited mutation helper path (`applyCapAuditedTeamMutation(...)`) today, but the authority of that path is enforced by live wiring rather than by a hardened structural contract. There is no mechanism that prevents a future contributor from adding direct local update logic or an alternate save route that bypasses audit generation, post-state validation, or rollback behavior — potentially preserving the visible save flow while quietly regressing mutation integrity. The audited path needs to be more explicit and harder to circumvent, with durable guardrails that pin the full UI-to-validation-to-persistence chain as a system. CS-5A structural hardening landed in live code, but this issue remains open until the requested validation set is fully green. | OPEN   |
| CS-5-2   | CS-5B           | MEDIUM   | Resolved by extracting an explicit prepared lifecycle contract inside `useArchitectActions.ts`, so manual dead money and exception mutations now carry one bound preview/apply/validate/persist/rollback descriptor through `applyCapAuditedTeamMutation(...)`. Preview snapshots, cap-audit generation, post-state validation, optimistic local apply, authoritative persistence linkage, and persist-failure rollback are now structurally tied together, and focused guardrails pin the invalid-preview, success-linkage, and rollback cases against future drift.                                                                                                                                                      | RESOLVED   |
| CS-5-3   | CS-5C           | MEDIUM   | Resolved by narrowing the public `useArchitectActions.ts` surface so authoritative Cap Sheet mutations remain exposed as first-class action handlers while weaker local-only contract-editor / raw-roster / reset mutators are no longer public peers. DEV-only fixture mutations now sit behind explicit `capSheetDevTools` / `teamHistoryDevTools` namespaces, `EditContractModal` no longer falls back through a local-only save callback, and focused guardrails pin the new mutation-class boundary against regression.                                | RESOLVED   |
