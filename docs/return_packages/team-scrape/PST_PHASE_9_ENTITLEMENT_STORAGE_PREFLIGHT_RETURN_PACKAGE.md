# PST_PHASE_9_ENTITLEMENT_STORAGE_PREFLIGHT_RETURN_PACKAGE

## 1. Firestore Path Map

We propose a **Referenced-Based Model** that separates Asset Definitions from Team Ownership, consistent with Architect's copy-on-write philosophy.

| Layer | Path | Purpose | R/W Access |
| :--- | :--- | :--- | :--- |
| **Layer 1: Base Definitions** | `architect_baseEntitlements/{id}` | Read-only source of truth for all 2026-2033 assets (generated by Phase 8). Contains full `EntitlementAsset` object. | **Read**: All<br>**Write**: System (Scrape/Gen) Only |
| **Layer 2: World Overrides** | `architect_worlds/{worldId}/entitlements/{id}` | Stores **deltas** for existing assets (e.g. changed protection) and **full objects** for new assets (e.g. created picks). | **Read**: World Context<br>**Write**: Architect Actions |
| **Layer 3: World Holdings** | `architect_worlds/{worldId}/teams/{teamCode}` | The Team Snapshot contains an `entitlementIds` array. This is the authoritative **inventory** of what a team owns. | **Read**: Team Page Load<br>**Write**: Trade/Sign Logic |

---

## 2. World Holdings Model

### Ownership Representation

Ownership is represented **by Reference** in the Team Snapshot.

**Schema:**

```typescript
interface WorldTeamSnapshot {
  // ... existing fields (roster, caps, etc.) ...
  
  // Replaces legacy 'draftPicksInventory' (which contained full objects)
  entitlementIds: string[]; 
}
```

### Why this Model?

1. **Lightweight Team Updates**: Trading a pick only requires moving a string ID between `teamA.entitlementIds` and `teamB.entitlementIds`. We **avoid** rewriting the heavy `EntitlementAsset` object (protections, history, conditions) inside the Team Doc.
2. **Single Source of Definition**: The terms of the pick (swaps, protections) live in `baseEntitlements` (or the World Override). Changing protections only requires writing to the Entitlement Override, not finding and updating the Team Doc.
3. **Performance**: Loading a team page requires fetching the `TeamSnapshot`, then performing a batched fetch of the `entitlementIds`. This is efficient in Firestore.

## 3. Override vs New Asset Rule Table

This table defines when to create a World Entitlement Override versus a Brand New Asset.

| User Action | Logical Outcome | Storage Action |
| :--- | :--- | :--- |
| **Trade an Entitlement** | Change Ownership | 1. Update `TeamSnapshot.entitlementIds` (Move ID)<br>2. Update `WorldEntitlement.holderTeam` (Sync query field) |
| **Modify Terms** (e.g. Add Protection) | Asset Mutation | Create/Update `architect_worlds/{wId}/entitlements/{id}` with **Partial** (Only changed fields) |
| **Exec. Exercise Swallow/Swap** | Asset Consumed/Mutated | Update `architect_worlds/{wId}/entitlements/{id}` (e.g. mark `spent: true` or update description) |
| **Create Brand New Pick** | New Asset Creation | 1. Generate new UUID<br>2. Create `architect_worlds/{wId}/entitlements/{newId}` (Full Object)<br>3. Add ID to `TeamSnapshot.entitlementIds` |
| **Split an Asset** | 1 Destroyed, 2 Created | 1. Mark Parent ID as `inactive` in World Override<br>2. Create 2 New Assets in World Overrides<br>3. Update Team IDs |

## 4. Rendering Resolution Order

The Trade Machine (and Team Page) resolves the "Effective Entitlement" for a given `id` using this robust chain:

**Resolution Logic:**

```javascript
EffectiveAsset = 
  Merge(
    BaseEntitlement.data() || {},        // Layer 1 (If exists)
    WorldEntitlementOverride.data() || {} // Layer 2 (If exists)
  )
```

**Conflict Rules:**

1. **Existence**: If ID exists in World but not Base, it is a **New Asset**.
2. **Ownership Truth**: While `EffectiveAsset.holderTeam` exists, the **Team Snapshot's `entitlementIds` list is the Authorization Authority** for "Can I trade this?". The system must keep them in sync, but the List governs the Team Page.
3. **Partial Overrides**: World Overrides are deep-merged. If World Override has `{ description: "Updated" }`, it inherits `seasonYear`, `round`, etc., from Base.

## 5. Save / Load Flow

### Scenario: Loading a Team's Assets

1. **Fetch Team Snapshot**: `get(architect_worlds/{wId}/teams/{teamCode})`
    * Read `entitlementIds` array (e.g. `['ent:LAL:2026:1...', 'ent:LAL:2027:1...']`).
2. **Batched Fetch Assets**: `getAll(entitlementIds)`
    * Internally, the `AssetLoader` resolves each ID:
        * Check `architect_worlds/{wId}/entitlements/{id}`
        * If not found (or partial), fetch `architect_baseEntitlements/{id}`
        * Merge and return.
3. **Return**: List of `EffectiveEntitlement` objects.

### Scenario: Trading an Entitlement (LAL sends Pick to NYK)

1. **Load**: Load both Team Snapshots (LAL, NYK).
2. **Verify**: Check LAL owns `entId`.
3. **Mutate LAL**: Remove `entId` from `LAL.entitlementIds`.
4. **Mutate NYK**: Add `entId` to `NYK.entitlementIds`.
5. **Mutate Asset (Optional but Recommended)**: Create/Update `architect_worlds/{wId}/entitlements/{entId}` setting `holderTeam: 'NYK'`. (Maintains indexability).
6. **Save**: `batch.commit()` updating 2 Team Docs + 1 Entitlement Doc.

### Scenario: Saving a New "World"

1. **World Metadata**: Create `architect_worlds/{newWorldId}`.
2. **Teams**: Teams are lazy-loaded. No immediate team writes needed until modified.
3. **Entitlements**: Entitlements are lazy-loaded. No copies made.
4. **Result**: Instant world creation (zero data dupe).

## 6. Backward Compatibility (Legacy draftPicks)

* **Deprecation**: The `draftPicks` and `draftPicksInventory` arrays in the `BaseTeamDoc` / `WorldTeamSnapshot` schema are **DEPRECATED**.
* **Migration**:
  * Existing logic that reads `team.draftPicks` must be refactored to use the `useTeamEntitlements(teamCode)` hook (which performs the ID fetch).
  * **Interim State**: During Phase 9/10, we can populate `draftPicksInventory` with the *resolved* entitlement objects at runtime (in the API layer) so legacy components don't break, but the *database* only stores the IDs in the new field.

---

## 7. Explicit Non-Goals

* **No Real-Time Indexing**: We are not building a collection-group index for "Find all picks owned by LAL across all worlds". Ownership is world-scoped.
* **No "Pick Protection" Parser**: This model stores the *result* of protection changes (strings/metadata), it does not yet include the logic engine to *execute* the protection logic dynamically.
* **No Legacy Data Migration**: We are not back-porting old worlds to this model. This applies to new worlds/trade machine sessions only.
