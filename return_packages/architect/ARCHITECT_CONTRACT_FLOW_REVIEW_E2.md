# Architect Contract Flow Trust Review E2

Code-trace-only review against the current worktree on 2026-03-22. No runtime code changes were made for this review.

## Executive verdict

`NOT TRUSTWORTHY YET`

The authoritative mutation pipeline is strong on sequencing and atomic batch persistence, but the two primary reviewed flows still have trust blockers. Sign-and-trade and offer-sheet finalization both persist team snapshots without corresponding player-override updates, which means the saved world can look correct in team/roster UI while later authoritative `getPlayer` reads remain stale. Offer-sheet storage also resolves player state through the offering team path, which can miss world-specific home-team overrides before validation and mirroring. UI validation also drifts from authoritative logic, especially around sign-and-trade first-apron enforcement.

## UI Validation vs Authoritative Validation Drift

Is drift currently present?

- Yes.

Where it is confirmed:

- Sign-and-trade first-apron logic is confirmed drift. UI validation checks the current/source team cap hit, while authoritative SAT validation checks the receiving team’s post-trade salary and hard-cap state.
- Offer-sheet modal preflight is confirmed drift-prone because the UI never validates the canonical offer-sheet flags/status that the authoritative `validateSigning` logic depends on.
- No-world sign-and-trade availability is confirmed drift across entry surfaces. FreeAgentPool world-gates it, but the dashboard modal can still expose it and rely on the handler to reject it later.

Where drift is only potential:

- `handleSaveContract` is currently fallback-only in the reviewed dashboard path, but if another surface uses it as the primary save handler, it would create committed-looking local truth without authoritative persistence.
- Offer-sheet finalization currently rebuilds a partial contract object instead of using `normalizeContractForWorld`. Current consumers may tolerate that shape, but it is a real canonical-shape drift risk.

What should be SSOT going forward:

- The mutation pipeline should remain SSOT: `validateSigning`, `validateOfferSheetResolution`, `buildPostTradeTeamsSnapshot`, `validatePostTradeSnapshotForContext`, `validateSignAndTrade`, and `validatePostStateCapLegality`.
- UI surfaces should not independently re-implement SAT apron logic or offer-sheet resolution logic. They should either call a shared preflight helper built from the authoritative stack or render authoritative preflight results directly.

## Preview/local state truth model

- `handleSaveContract` is explicitly local-only preview code. The comment says it “updates local state only,” and the implementation directly mutates `teamCapSheet` plus `capHolds` without calling `runAuthoritativeFAMutation`, `persistMutation`, or `applyWorldMutation`. Evidence: `src/features/architect/GMDashboard/hooks/useArchitectActions.ts:2655-2735`.
- In the current reviewed GMDashboard path, `handleSaveContract` is not the primary commit path for sign/resign. `EditContractModal` prefers `onSignFreeAgent` / `onResign` before `onSaveContract`, and `GMDashboard` passes both authoritative handlers and the local fallback. Evidence: `src/shared/components/EditContractModal.tsx:1141-1159`; `src/features/architect/GMDashboard/GMDashboard.tsx:188-196,540-556`.
- Trade Machine SAT modal behavior is intentionally preview/local until `applyTradeToCapSheet` dispatches `executeTrade`. `TradeEditor.handleTradeMachineSignAndTrade` only updates local trade state with `setPlayerTrade`; the world write happens later via `useArchitectActions.applyTradeToCapSheet`. Evidence: `src/features/architect/tradeMachine/TradeEditor.tsx:396-470,765-779`; `src/features/architect/GMDashboard/hooks/useArchitectActions.ts:1428-1554`.
- For the current primary free-agency contract path, I did not confirm a “saved-looking local-only commit” bug. The more serious trust problem is different: successful sign-and-trade and offer-sheet-finalization commits can leave the persisted world internally inconsistent because team snapshots update but player-override reads do not.
- UX messaging is sufficient for the Trade Machine preview branch because that surface is inherently an editor/preview tool. It would not be sufficient if `handleSaveContract` were ever reused as a primary save path, because that handler returns success after local mutation with no built-in preview-only messaging.

## Trust blockers

- Sign-and-trade inherits the broader trade persistence bug where successful commits do not update player override docs, so authoritative `getPlayer` reads can remain stale after a saved SAT.
- Offer-sheet finalization does not emit player updates or explicit old-team cleanup, and it bypasses the canonical signing cleanup path.
- `storeOfferSheet` resolves player state through the offering team path, which can miss world-specific home-team overrides before validation and mirroring.
- UI SAT validation is not aligned with authoritative receiving-team hard-cap logic.
- Offer-sheet resolution still allows late matches because the 48-hour window is warning-only.

## Recommended next ticket list (ordered)

1. Fix trade/sign-and-trade persistence so trade-based flows emit canonical `playerUpdates` and explicit old-team player-override cleanup/deletes, then add regression tests that call `getPlayer` after a saved trade/SAT.
2. Refactor offer-sheet finalization to reuse a shared canonical signing/movement helper so matched/declined finalization gets contract normalization, cap-hold cleanup, player override updates, and old-team cleanup.
3. Fix `storeOfferSheet` player loading so the authoritative flow resolves current world player truth from the actual home-team/player owner, not the offering team path.
4. Replace modal-side SAT apron logic with shared authoritative preflight based on receiving-team post-trade context.
